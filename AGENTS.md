# AGENTS.md — правила проекта alt-image-update-operator

## Product goal

Build a real Kubernetes operator for automating security-oriented rebuilds of ALT Linux based container images and declaratively rolling the rebuilt image into a target Kubernetes Deployment.

This is a thesis project, but the software must work. Do not implement fake success paths in runtime code or e2e scripts.

## Expected stack

- Language: Go.
- Framework: Kubebuilder and controller-runtime.
- API group: `security.altlinux.org`.
- API version: `v1alpha1`.
- Main CRD kind: `AltImageUpdatePolicy`.
- Runtime target: Kubernetes cluster, preferably kind/minikube for e2e.
- Build job: real Kaniko or BuildKit job. Default: Kaniko.
- Demo registry: local registry attached to kind.

## Repository layout

Expected layout after scaffolding:


## Build and validation commands

Use the commands generated by Kubebuilder when available:

```bash
gofmt -w <changed-go-files>
go test ./...
make generate
make manifests
```

For e2e, prefer a script such as:

```bash
hack/e2e.sh
```

The e2e script should create or use a kind cluster, install CRDs/controller, create a local registry or use an explicitly configured registry, apply a demo Deployment, apply an `AltImageUpdatePolicy`, wait for Job completion, verify Deployment image update, and verify CR status.

## Engineering rules

- Implement one task at a time when invoked by Ralph.
- Keep changes scoped to the assigned task.
- Do not remove or rewrite unrelated files.
- Use gofmt for Go files.
- Prefer idiomatic controller-runtime patterns.
- Reconcile logic must be idempotent.
- Do not create duplicate Jobs for the same generation/build key.
- Do not update Deployment repeatedly when the desired image is already applied.
- Do not log registry credentials or Kubernetes Secret data.
- Use Kubernetes conditions for status.
- Use owner references for Jobs created by the controller when appropriate.
- Runtime code must not depend on unit-test fakes.

## Required product behavior

The MVP is complete only when these behaviors are implemented:

1. CRD can be installed into a cluster.
2. User can create an `AltImageUpdatePolicy` that references a target Deployment and container.
3. Controller reconciles the CR.
4. Controller creates a real Kubernetes Job for check/build according to policy.
5. Build Job performs a real image build and push, not a fake echo.
6. Controller observes Job completion.
7. Controller updates target Deployment image.
8. Controller updates CR status with phase, conditions, timestamps, Job name, built image, and applied image.
9. Tests cover API defaults/validation, reconcile paths, status transitions, and Deployment update.
10. Demo/e2e proves the workflow in a real cluster.

## Testing expectations

- Add unit tests for pure helper logic.
- Add envtest/controller tests for reconciliation when feasible.
- Add e2e/demo script for the full workflow.
- If a validation command cannot run because the environment lacks a tool, document the exact reason in `progress.txt` and still run all available checks.

## Cluster safety

- Do not run `kubectl`, `helm`, `kind`, `minikube`, or e2e commands against the developer laptop default kubeconfig.
- The developer laptop kubeconfig may point to unrelated production or work clusters. Treat local `~/.kube/config` as unsafe unless the user explicitly says otherwise for the current task.
- The only Kubernetes cluster allowed for real e2e/demo work is the remote minikube host reachable with:

```bash
ssh clouduser@185.120.186.138
```

- Run live-cluster commands on that remote host over SSH, or use an explicitly provided kubeconfig that is confirmed to target only that remote minikube cluster.
- If a validation command needs a live cluster and the remote minikube node is `NotReady`, mark the task `blocked` or skip only that live-cluster validation as appropriate for the task, and record the exact reason in `progress.txt`.
- Never apply manifests, install CRDs, run controllers, or execute e2e scripts against a cluster unless the target cluster has been explicitly confirmed as the allowed remote minikube.

## Documentation expectations

Document:

- CRD fields and example YAML.
- How to run locally.
- How to run e2e.
- Demo steps for thesis defense.
- Known limitations.

## Do not do

- Do not implement only documentation without code unless the task explicitly asks for docs.
- Do not replace image building with a script that just writes a successful status.
- Do not hard-code one namespace unless the PRD/task explicitly restricts it.
- Do not mark tasks done when validation failed.
